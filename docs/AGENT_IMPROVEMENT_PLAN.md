## 实施前产品就绪判断（2026-10-15，只读复核，后续实现见上节）

结论：核心架构方向符合目标，已有可创建固定版本并真实交互的基础；尚不属于
“普通用户描述复杂需求后，稳定执行、修改、验证并可靠复用”的成熟交付版本。
不能用服务reload或当时1779/753测试计数推导完整真实业务已通过。当时源码
manifest与该门禁一致、API健康；包装v1仍max_turns16，原Run仍failed/runtime_timeout。

如果重复上次从第10轮再用4个actor的路径，当时出图前仅余2轮、最低交付需4轮，
会在图片收费前被budget stop；新实现改为保存动作并等待明确续额。不是所有v1
路径都必然失败：减少错误或多余动作
仍可能留足余量；尚无新真实测试证明。延长review timeout不等于响应更快。

本轮新增的必要缺口是失败后的执行断点。包装最新checkpoint仍在第10轮human
input等待点，不是已完成状态写后的execution断点；RuntimeService只接受最新
execution checkpoint恢复。整次retry只要历史出现tool.started就拒绝，这保证
未知/已执行效果不会盲目重放，却没有提供本案状态核对后继续交付审查的路径。
不能通过删除retry guard或重新整案生成解决。需与预算一起重做执行生命周期：
记录已完成步骤/收据/状态修订/候选及资产，区分已知纯观察和有/未知效果，安全
暂停、明确续额、继续未完成阶段，保持固定版本及总计；断点完整性不足时明确
告知不可自动恢复。实现须同时验证进程中断、超时、部分完成与重复命令。

质量评估分开：工程契约与本地回归已有证据；文字三方案/选择/一次修改有单次
真实证据；真图、跨视角一致性、状态关联与最终交付未通过；生成/运行成功率、
业务误报漏检、p50/p95及实际Token/费用缺可重复基线，不给虚假的产品总分。
现有算术结果不替代价格来源，视觉模型判断不替代物理认证。

最近阶段退出条件：预算/断点恢复与完整效果核对先本地验收；新单独授权后跑
完原包装要求的四视角、修改、状态历史及交付检查；生成质量与业务结果分层
形成报告，再建立多任务/故障的重复基线。Provider-native工具协议和动态
Supervisor/并行不是成熟产品的必选项，不为了模式齐全扩大本阶段范围。

## 2026-10-15：上一阶段预算、审查时延与四种模式复核（历史，后续实现见首节）

执行预算与生成预算、Provider 额度及 HTTP 超时是不同边界。包装固定 v1
的 max_turns=16 按整个 Run 累计，行动、纠错、追问及必需审查均消耗它；
回复/审批不重置。当时平台默认8、契约上限32，composer按工具有无选择16/8，
当时尚无用户续额；现由首节统一配置和续额路径取代。最近真图续接
直接失败于 pre_render runtime_timeout，而非 budget error，且0图片请求。
只是去掉轮次限制不能修复超时、错误参数、错误编译或账户额度。

当前生产 FactorySettings.repair_attempts 默认 None，FactoryService显式
传给Planner，不再默认独立限制为三次；总请求默认8、时间600s仍有界，操作
授权可更低。底层Planner兼容构造默认3仍保留；不能把历史默认三次描述成
当前产品所有调用都必经的硬门槛，也不能把None写成无限收费重试。

本轮本地实现：同 RuntimeModelClient / transport / 模型 / 凭据的
complete_review，独立可配置 read timeout 默认180s、上限300s，普通行动
默认90s不变。连接/写入/pool不扩大；这是HTTP阶段超时，不是整个Run期限，
也不是时延提升证明。Provider异常不重试，审查失败保存phase/code/安全
diagnostic/elapsed_ms，候选不发布；实际预审失败不生成图像。

事件与桌面同步显示 run_model_turns 的 used/limit/remaining，以及额度不足
时必需交付的最少余量。包含失败审查尝试，不代表实际Token/金额/图像数量；
旧事件缺证据不补造预算或原因。审批与回复恢复不双计/重置。三个新事件的
Python分类、正式JSON Schema、TypeScript客户端已同步。

四种模式当前边界：Reflection已有规则/只读模型审查与同Run返工，尚无通用

## 判断与修正

参考讨论的主方向成立：需要把需求、可执行验收、构建、运行、评价与修复连接起来。
但不能用“15 步中完成几步”表示可靠性。一个步骤可能已有实现而缺真实验收，也可能
已有特定业务测试而缺通用产品入口。完整闭环必须以具体任务及证据核对。

- 需求快照和共享引用解析已经实现，不能继续写成尚未开发。最新真实失败已越过
  这两处，变成原生动作与外部门禁归属错误；此前缺 Writer 和限流分别处理。
- 算术、原生 CSV 对比及带标准答案的脚本模型测试已经存在。缺口是将任务级验收
  产品化，并证明真实自然语言生成也选择、使用了这些能力。
- 业务真值不必只能由用户提供。可来自用户确认、组织规则、可信资料、独立计算和
  人工设计的测试答案。模型生成的答案或另一个模型的赞同不能自动成为独立真值。
- “所有能力 ready 才能 Apply”过严。可以保存标明 Needs Setup 的可审查 Draft。
  必需能力缺失必须保留为显式缺口；运行就绪检查不能让这些缺口在编译后消失。
  未实现、未配置、未授权、不适用应分开，不能把缺口一律转为让用户缩减需求。
- 完整需求作为共享任务背景是合理的。需要改善的是角色职责、真实输入输出和停止
  条件；不必新增平行 RoleBrief 管线，也不应通过删除原始上下文解决指令问题。
- loop 已逐轮根据工具观测选择动作，不能称为完全没有运行时调整。缺少的是明确的
  可更新计划、业务验收反馈与执行期修改提案。
- 分支干跑可以证明指定替身场景下的路由。它不能证明真实模型会遵从门禁、外部
  工具副作用安全或所有组合已覆盖；组合上限与未覆盖路径必须显式记录。
- 有限返工不能直接向现有 Workflow 添加回边。当前契约是 DAG，应先用自治 Agent
  内部迭代；确有跨角色重复需要时，再设计版本化、有界的重复执行语义。

## 限制应如何调整

可以删除不代表任务或权限语义的限制：固定人数才算多 Agent、按 main/editor 名称
排除角色、单因 state 就强制 Workflow、已核准只读错误直接终止。本轮已调整这些点。

审批以实际对象为准：选择/补充业务事实、确认方案和授权副作用是不同语义，但不
应机械显示两次相同确认。同一次确认能锁定报告快照、实际 Tool 参数和授权范围时，
设计为一次审批；不能因为业务审批通过就推导任意后续写入授权。固定保存动作能由
确定性 Tool 完成时，不为“多 Agent”形式专门增加一个只负责保存的 LLM 角色。

应改为可配置预算：最大轮数、模型请求次数、构建修复次数、工具输出详情量和批次
规模。默认值可以保留；扩大或取消固定上限前，应有总调用、时间、Token 或明确费用
预算、停止按钮、停滞检测和可恢复状态。预算属于 Runtime/Harness，不写成业务能力
限制；不通过无限重试补偿规划或协议错误。

需要有配套机制后扩展：Condition 的表达式能力、并行、跨角色返工、动态委派、原生
Tool Calling 和可执行资源生成。优先使用成熟解析/执行库及既有适配器，避免任意
eval、生成代码直接执行或为了支持复杂需求增加职业关键词分支。

继续保留：显式授权、真实工具收据、独立 verifier outcome、不可变版本、路径与
Secret 边界、审查后精确 Apply、revision/ETag、权限变化可检查、未知副作用不盲重试。
这些边界应可解释和可操作，不能用泛化的安全理由拒绝已经授权的正常任务。

## 目标流程

1. 保留原始需求及有序修改，区分构建时缺软件能力与运行时缺业务事实。
2. 形成成功条件和可检查方法；缺乏真值的条件显式等待证据或人工判断。
3. 模型生成 TaskStructure，并精读选中的真实 Skill 方法。
4. 按自主职责、显式交接和业务门禁选择 Agent / Workflow，编译真实契约。
5. 解析模型、工具、知识与权限；形成诚实的缺口清单，不丢需求。
6. 静态校验、可选结构路径检查和 TaskCoverage，生成精确审查提案。
7. Apply Draft；测试使用冻结候选快照，正式 App 执行显式 committed 版本。
8. 在隔离范围内用固定用例运行，收集模型调用、工具、审批、产物及失败证据。
9. 对照每条成功条件评估结果；区分执行完成、契约通过、模型评审和业务验收。
10. 将可定位的失败变成受预算控制的纠错，或生成需审查的修改提案。
11. 固定版本与用例集；编辑后比较同一用例集，重复使用时保留真实运行证据。

这是一条复用现有 Builder / Proposal / Runtime 的闭环，不是另一套生成框架。

## 分阶段实施

### 阶段 0：补完普通用户生成与交付主线

目标：完整需求生成真实能力，固定版本运行产出正确且可打开的交付物。

- 对最新已验证 TaskStructure 零 Provider 复放，区分模型漏职责、编译器丢职责与
  覆盖审查判断错误。保留安全的修复失败原因，避免只显示第一次覆盖缺口。
- 核对文件选择、计算、列名追问、展示异常、用户确认、报告写入与执行记录各自的
  承载角色、资源和数据绑定。缺写工具不能靠 instructions 中提到写报告来兑现。
- 优化审批对象和保存动作：评估明确绑定快照的一次确认，或审批后直接执行已声明
  的确定性 Tool；需要 Writer 推理或改变交付内容时才保留独立角色和相应效果审核。
- 让工具的公开结果契约真实描述行号、源 hash、精确金额与截断信息；通过新版本
  扩展契约，保留旧 pin，不静默改变已锁定资源。
- 复用 TaskActor、TaskStage、真实 Skill 和 typed I/O 提供角色任务简报。完整需求
  保留为背景，角色只拥有自身职责和允许动作。不增加每个角色一次固定模型调用。
- 补原文件保护：写范围受限于 reports 不等于不能覆盖输入。对实际读取/选择的
  文件保存来源，并在写入授权和审批恢复后阻止覆盖原输入，包括输入本来在 reports
  内的情况；跨父 Workflow / 子 Agent 的保护范围必须一致。
- 本轮反馈与自主性改动验证后，先复现内部问题，再进行一次有明确证据目标的真实
  构建。429/环境错误与规划错误分开；没有新修复依据时不重复付费调用。

退出标准：CSV 主要异常、正常拆分付款、精确合计、原始行号、两类拒绝无写入、
原文件 byte/hash 未改、可打开报告全部有证据；真实模型生成与脚本 fixture 分开。
同时保留研究整理、交互修改和跨 Run 状态更新的代表用例，避免为 CSV 特判生成器。

### 阶段 1：将验收规格与确定性评价产品化

复用 `TaskStructure.success_criteria`，为每条条件增加稳定 ID 与检查绑定。
建议对象为 `EvaluationSpec`、`EvaluationCase`、`EvaluationReport`，具体契约名称
和持久化结构在实施时确定；不并行新增另一套 TaskSpec 或 Source 真相。

条件记录原始来源、必需/建议等级、检查方法、实际输入/输出/收据/产物 subject、
期望事实或量规、真值来源与版本。每个 case 冻结显式选择的数据引用、hash、预期值、
适用场景和授权边界；完整私有文件和真实凭据不进入 Source、日志或社区导出。

先实现有确定答案的检查：

- 实际类型与支持的 JSON Schema，包括 required、enum、multiple 和嵌套字段。
  本轮 loop final 已实现有界离线子集；不能据此宣称 Workflow Verifier 也完成。
- Artifact/报告在实际存储中可解析、可读取，hash、所属 Project 与输出引用一致。
- 精确金额、数量、集合和业务分类与独立答案对比；金融数值默认精确比较，只有
  明确业务规则允许时才采用容差，不能用浮点误差当正常差异。
- 输入未改、拒绝无写入、权限作用域、副作用收据与实际文件内容一致。
- Entity 同一身份跨 Run 更新、历史 revision、歧义记录先确认；补并发 stale revision
  和重复创建的失败场景，不能把 revision history 当成已实现乐观并发保护。

单条件状态：pass / fail / unknown / not_evaluated / awaiting_human。
报告判定：accepted / rejected / inconclusive，独立于既有 Run.status。
accepted 需要全部必需条件通过及必需人工确认完成；没有证据就是 inconclusive，
不自动按通过处理。模型量规意见另记 judged，不成为确定性真值。

退出标准：刻意构造的错误金额、缺行号、空文件、坏引用、输入被修改和未批准写入
均被相应验收器捕获；合法拒绝与合法无结果不能被误判为业务失败。

### 阶段 2：安全的用例集、路径检查与版本回归

- 批次冻结 Source/version、EvaluationSpec hash、case/data hash、模型与资源版本；
  每个 case 有独立 Run，与原始评估记录可追溯关联。
- 默认隔离 Project、SQLite、文件根与替身外部写工具。实际 SaaS、发布、付款、
  主机 Shell/MCP 等副作用需要独立授权；测试模式不得自动批准真实用户工作。
- 枚举 Condition、业务审批、Tool 审批、HumanInput 与 Verifier 的实际可达路径，
  记录无解约束、未覆盖路径和组合预算。不伪造统一的 passed Verifier。
- 批次批准/拒绝的预设只能在隔离 fixture 中使用。生产 Run 的授权仍由用户或
  已批准策略决定，不从 expected result 推导授权。
- 显示运行完成率和业务验收通过率；unverified 不等于业务 accepted。
- 回归比较同一 case 集与评估器版本；不把新的评估器或更宽的容差混为 Agent 改进。
  修改检查标准本身需要独立可审查差异，不永久冻结原本错误的测试答案。
- 私有评估记录、Run 关联和数据引用保存到应用数据边界。明确可分享的规格与
  脱敏样例可以由用户导出；不自动把原始数据写入 Project 包或 Community。

退出标准：数据/模型缺配置、批次预算耗尽、取消、服务中断、重复提交与部分失败
均有准确终态；取消不续跑，已执行的调用收据不丢失。新版本退步按条件逐条展示。

### 阶段 3：执行期 Reflection 与有证据的修改提案

- 先使用已有错误码、收据和验收结果定位环境、授权、数据、绑定、工具、指令或
  规划问题。模型可补充诊断，但须引用具体证据，不能凭 final 文本猜测执行情况。
- 同一 Run 内：只读或纯计算失败、参数错误、输出契约错误可回给自治 loop 调整
  下一步。写入效果未知时先查结果或请用户处理，不能自动重放。
- 跨版本：有业务失败时生成既有 Edit Proposal，包含原因、目标层、真实 source
  diff、权限/依赖影响和同一 case 集重跑计划；确认后 Apply，不自动修改 committed。
- 原始职责、写范围和验收必需项的变化都需解释。用户明确改变需求时允许改标准，
  不把模型最初猜测的绑定、字段或方法永久冻结成不可修正的业务约束。
- 独立评审模型可选，记录具体模型、量规和证据来源；同模型可保留，但明确其
  相关性。没有可判标准时先补标准，不能靠增加 critic 数量生成质量证明。

退出标准：故意错误可定位到正确层，修复产生最小相关差异；重跑修复目标条件并
保留原本通过的必需条件。环境/429 不触发盲目的改指令或权限扩张。

### 阶段 4：可调整的规划与成熟预算

- 给自治 loop 增加短的公共任务计划和进度：目标、下一步、已完成事项、依赖及
  待用户决定。记录可观察行动，不存储或展示隐含 chain-of-thought。
- 工具/验收/用户反馈触发显式 plan update，保留完整需求，说明调整依据；不强制
  每个简单任务先调用一次独立 Planner，也不让代码预设所有业务步骤。
- 逐步将 max_turns 与修复预算的硬编码改为用户/主机策略可配置的上限。默认
  有界；与总模型调用、时间、Token/费用预算及停滞检测一起实现。
- 记录 Provider 实际返回的 usage；价格来源、币种、时间及估计/实付区分。没有
  usage 或计费信息时展示 unknown，不能把请求字节数当 Token 或费用。
- 扩充 Condition 时采用类型化表达式与统一解析器。支持嵌套值/集合/布尔组合
  要同时完成 Schema、绑定、Runtime、错误反馈和 UI；不引入任意 eval。
- 原生 Tool Calling 作为 capability-aware transport：支持时使用，未知或不兼容
  时保留 JSON action 回退。工具授权、审批、收据与结果校验只维护一套。

退出标准：反馈确实改变下一步而不删除目标；长任务不会因随意固定轮数被截断，
但预算/取消/停滞能准确停止；不同 Provider 的输出协议不改变权限和结果语义。

### 阶段 5：按需要扩展协作与有限返工

首先完成现有 Workflow 的 typed handoff、父子 Run 关联、等待用户/工具审批转发、
失败与取消传播。研究、审查、写入等角色是否独立以任务收益和权限隔离判断，
不按职业名称或固定人数拆分。

独立角色可并行时，再增加声明式并行与结果合并：确定性调度器管理并发和资源
冲突，模型负责选择任务，不授予调度、权限或文件写锁的控制权。

动态委派需要先声明允许调用的 committed Agent 版本、输入输出契约、子任务预算、
最大深度、父子 Run、用户授权范围和可见终态。子 Agent 不因被委派获得父权限，
Supervisor 也不能创建未知 Agent、工具或绕过子任务审批。

跨角色返工先采用显式有限迭代与同一验收标准。确需扩展 Workflow 契约时设计
有界重复原语或子流程，不直接破坏 DAG 假设，不静默重写旧 Workflow 版本。

退出标准：结构化结果真实传递；父停止后子任务无新增效果；写入角色在审查/审批
通过前不可执行；一个 Agent 足够的任务没有额外协作开销。

## 分模块评测标准

需求理解：原始条件与有序修改可追溯；助手解释不升级为要求；重试不混后续任务。
合理的业务事实缺口变成具体问题，能力不支持不伪装为可通过追问解决。

Planning：所有必需职责有真实承载；角色、输入/输出、状态、门禁和产物可实现。
修复可纠正错误绑定，但不能悄悄降需求；未知/未来/歧义引用有可操作的诊断。

Skill：准确 pin/hash 和实际方法适用；所需 executor 已解析；不将 Skill 名称当
能力证明；未配置、未读方法、选择歧义有诚实状态。

Tool：模型看到真实公开契约；参数与结果校验一致；前置授权、审批、执行、收据
与 verifier outcome 可核对；可信只读失败能调整行动，未知副作用不能盲重试。

Model：任务能力与 transport 匹配，凭据/模型选择由已有授权决定；请求 receipt
能区分构建模型与执行模型。推理参数配置不等于已证明业务推理能力。

Agent：自主 loop 能调用工具、提问、接受反馈、按预算停止；typed final 与实际
Artifact/文件绑定成立；内容正确性由任务验收决定。

Workflow：每个 AgentCall 固定版本；真实类型交接；条件/审批/Verifier 的所有
要求路径有相应证据；失败/拒绝合法输出、子 Run 等待和取消均保留语义。

Reflection：反馈引用实际错误和结果；修改改善目标条件且不导致既有必需条件退步。
模型评价与确定性验收分开，低置信度或证据冲突显式 unknown。

交付：用户审查的是最终候选、真实测试版本及报告；source/behavior/lock/data/
evaluation hashes 匹配。新版本不静默替换旧 Conversation 所绑定的版本。

## 指标与通过条件

硬门禁优先：未授权写入、越界、输入破坏、Secret 泄漏、静默版本改变或伪造证据
在任何代表用例中出现即失败。核心业务 case 的必需条件全部通过，不用平均质量分
掩盖一个金额、漏报或权限错误。负例也必须证明检查器确实能抓到错误。

生成一次通过率 = 首个候选通过契约和需求覆盖的任务数 / 有效构建任务数。
有界修复后通过率 = 预算内形成有效候选的任务数 / 有效构建任务数。
执行完成率 = 按定义正常结束的有效 Run 数 / 已开始的有效 Run 数。
业务验收通过率 = accepted 的 case 数 / 计划要求的全部适用 case 数。

环境失败、用户取消、等待人工、跳过、不适用、尚未评价和模型 judged 单列，不
静默从分母剔除，也不全部压成模型失败。对每个任务族分别统计，再呈现总体值。

同时记录需求遗漏、错工具/错绑定、协议错误、无效修复、重复错误、请求次数、
Token、耗时与可确定的费用。先建立基线与样本量，不凭少数真实运行宣称 95% 稳定；
目标值由任务风险、基线与用户预算决定。可重复的离线/原生 case 先覆盖充分，真实
付费验证保留独立预算、一次测试的证据目标及停止条件。

验收层次分别报告：本地单测/API/原生执行、脚本模型、真实 Provider、真实浏览器、
打包运行、Git/CI。没有运行的层次不因其它层次通过而算已完成。
